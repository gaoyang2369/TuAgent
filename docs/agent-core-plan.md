# TuAgent 开发计划 · 用 Python 实现 Pi 的通用 Agent 核心

## 1. 交付目标

交付一个可安装、可导入的 Python 库 `tuagent`。调用方提供模型，可选地提供系统提示词、工具和执行上下文。仅提供模型即可发起对话。注册一个异步函数后，同一个 Agent 入口就能完成“模型请求工具 → Python 执行 → 结果回传 → 模型继续回答”。

首版支持文本和函数调用。包中默认工具集为空。测试使用可编排的模型和在用例内注册的函数。M1、M2 构成可独立交付的通用核心，M3 是模型协议集成。具体业务能力、角色提示词和身份规则由未来的接入方提供。

### Pi 行为基线

以 Pi **v1.5.2** 的 `pi-agent-core` 为对照，移植可观察的行为，Python 接口按 `asyncio` 设计。[Pi Agent](https://github.com/earendil-works/pi/blob/v1.5.2/packages/agent/README.md)

| Pi 的行为 | TuAgent 的交付阶段 |
| --- | --- |
| 有状态的 Agent 管理会话，底层循环通过注入的模型接口推进。一轮包含一次模型请求和这次回复产生的一批工具调用。 | M1 实现会话、模型接口、循环、工具注册和执行。 |
| 助手声明的工具调用和对应结果进入历史。上游允许并行执行，写回历史时保持模型声明的顺序。输出被长度上限截断时，整批调用跳过执行。 | 首版采用串行执行。M1 实现消息配对与顺序，M2 验证截断、取消、事件和续跑。 |
| Pi 可在工具批次结束后接收 steering 输入，在本可结束时处理 follow-up，并可在每次模型请求前转换上下文。 | 首版保留独立的模型请求构造入口。交互队列、可配置上下文转换和并行调度作为可选的 Pi 行为扩展。 |

上游循环和测试可用来确认工具结果顺序、截断处理和续跑边界。[循环实现](https://github.com/earendil-works/pi/blob/v1.5.2/packages/agent/src/agent-loop.ts) · [行为测试](https://github.com/earendil-works/pi/blob/v1.5.2/packages/agent/test/agent-loop.test.ts)

## 2. 项目结构

采用 Python 3.11+、`asyncio` 和单个发行包。内部消息和事件用带类型的 dataclass，模型接入使用 `Protocol`。工具入参用 Pydantic v2，使同一份类型定义既能生成 JSON Schema，也能校验运行时参数。供应商 SDK 作为适配器的可选依赖。[Pydantic JSON Schema](https://docs.pydantic.dev/latest/concepts/json_schema/)

以下是首版完成时的目录，随里程碑创建相应模块。

```text
TuAgent/
├── pyproject.toml
├── src/
│   └── tuagent/
│       ├── __init__.py             # 调用方使用的公共 API
│       ├── agent.py                # 会话历史、运行入口、取消与续跑
│       ├── loop.py                 # 模型轮次、消息提交、继续与结束
│       ├── messages.py             # 用户消息、助手消息、调用、结果及运行状态
│       ├── model.py                # 模型接口、模型事件、构造模型请求
│       ├── events.py               # M2 对外的运行事件
│       ├── tools/
│       │   ├── registry.py         # 工具定义、注册和运行时快照
│       │   └── executor.py         # 参数校验、执行上下文和结果归一化
│       └── providers/
│           └── chat_completions.py # M3 首个真实协议适配器
└── tests/
    ├── fakes.py                    # 可记录请求并按脚本回复的模型
    ├── test_loop.py                # 由公共 API 验证轮次和历史
    ├── test_tools.py               # 注册、分派、校验与工具错误
    ├── test_lifecycle.py           # 取消、事件、上限与续跑
    └── test_provider.py            # 协议映射、分片与流结束
```

依赖方向为“调用方 → Agent → 循环”。循环只依赖模型接口和工具执行器，具体模型适配器负责协议转换。循环按注册名称分派调用，因此添加工具只需调用公共注册接口。

## 3. 公共接口与数据约定

| 接口或类型 | 职责 |
| --- | --- |
| `Agent(provider, *, system_prompt="", tools=None, context=None, max_turns=16)` | 一个实例持有一个内存会话。同一实例一次只推进一个 run。每次开始运行时固定提示词和工具快照。建议默认最多发起 16 次模型请求，调用方可指定其他正整数。 |
| `await agent.run(text) -> RunResult` | 追加一次用户输入并运行到终态。结果包含状态、本次新增消息、模型请求次数，以及可用的最终文本或错误码。M2 增加可选的关键字参数 `on_event`，供调用方订阅本次运行。 |
| `agent.abort()`、`await agent.continue_run()` | M2 提供主动取消和从合法会话边界续跑。续跑调用同一底层循环，沿用历史，无需补造用户消息。 |
| `ModelProvider.stream(request) -> AsyncIterator[ModelEvent]` | 请求包括系统指令、模型可见的消息及工具声明。适配器可以发出增量，成功时以一个完整助手回复和停止原因结束。M1 的脚本模型只需发出完整回复。 |
| `ToolRegistry.register(name, description, args_model, handler)` | 注册异步处理函数，重名在注册时抛错。模型可见的声明和实际查找使用同一份快照。 |
| `await handler(args, ctx) -> ToolOutput` | 处理函数接收已校验的参数。`ctx` 携带调用 ID 和可选的调用方上下文。`ToolOutput.content` 回给模型，可选 `details` 供应用读取。 |

消息至少有 `UserMessage`、`AssistantMessage`、`ToolResultMessage` 三种。`AssistantMessage` 允许同时携带文字和多个 `ToolCall`。每个调用保留 `id`、`name` 和参数，每条结果记录原始 `tool_call_id`、内容及错误标记。构造模型请求时显式投影字段，将工具实例、执行上下文和内部详情保留在进程内。

## 4. 一次 run 怎样推进

1. 取得会话运行权，冻结工具定义，追加用户消息。检查剩余轮数，构造本轮请求并消费模型流。
2. 收到完整回复后，先检查同批调用 ID 是否齐全且唯一，再提交助手消息。流式文字用于实时观察，只有完整且可执行的回复才触发处理函数。
3. 正常回复没有工具调用时返回 `completed`。有调用时按声明顺序查找工具、解析 JSON、校验入参、等待处理函数，并为每次调用追加一条同 ID 的结果。
4. 整批结果就位后再请求模型。若刚完成最后一个允许的轮次，保留工具结果并返回 `turn_limit`。请求失败、取消与正常完成分别返回对应状态并释放会话运行权。

下面是验收时应能检查的第二次模型请求。工具名和返回值均由测试在运行时提供。

```text
第 1 次模型请求    [用户消息]
第 1 次模型回复    助手消息，含工具调用 id=c1
执行器             调用测试注册的函数，得到值 V
第 2 次模型请求    [用户消息, 助手消息(调用 c1), 工具结果(c1, V)]
第 2 次模型回复    使用实际收到的 V 生成最终文本
```

| 情况 | 预期行为 |
| --- | --- |
| 未知工具、坏 JSON、参数校验失败 | 为相应 ID 生成明确的错误工具结果，该调用的处理函数执行零次。同批其他调用照常处理。 |
| 处理函数报告失败或抛出普通异常 | 将可提供给模型的错误归一化为工具结果，下一轮可以据此修正。 |
| 调用 ID 缺失或同批重复，或模型流在完成前断开 | 以 `failed` 结束该 run，保留此前完整历史，本次草稿触发零次工具执行。 |
| 收到长度上限标记 | 若携带可配对的工具调用，整批按原 ID 写回截断错误，并在轮数预算内继续。纯文本截断以 `incomplete` 结束。 |
| 工具批次中途取消 | 保留已完成结果。给未开始项记录 `not_started`，区分已启动但结果未确认的调用。补齐已提交调用的结果后结束本次 run。 |
| 显式续跑 | 历史末尾为用户消息或配齐的工具结果时，可继续请求模型。空历史和已正常结束的助手结尾返回清晰错误。工具结果不确定时，由调用方决定如何核对。 |

## 5. 实施顺序与可直接使用的开发指令

每个阶段都通过库的公共接口验收。建议使用标准库 `unittest.IsolatedAsyncioTestCase` 编写异步测试。开发环境安装项目后，统一用 `python -m unittest discover -s tests -v` 运行离线回归。

### M1 · 最小通用循环

> 从零创建可安装的 Python 库 `tuagent`，实现异步 Agent、内存会话、可注入的模型协议、工具注册表和执行器。默认工具集为空，系统提示词与执行上下文可省略。通过同一个 `Agent.run()` 支持直接回答和工具往返，提供可配置的轮数上限。用脚本模型和仅在测试内注册的函数做离线验收。交付库、测试和打包配置，本次做到 M1 验收通过。

**验收**

- 安装后可直接导入 `tuagent`。仅注入脚本模型，一次请求得到回答，首个请求的工具声明为空。
- 在测试中临时注册一个函数。脚本模型请求它一次，第二次模型请求包含原助手调用及同 ID 的结果。改变函数返回值，最终文本随之改变。断言模型请求两次、函数执行一次。
- 换一个注册名并让脚本请求新名称，运行同一组断言。重复注册同名工具会报错，无效参数写回错误且处理函数执行零次。
- 在同一实例连续调用两次 `run`，第二次输入可见先前已完成的会话。让脚本一直请求工具，运行在指定轮数处停止。构建的 wheel 只发布 `tuagent` 及其子包。

### M2 · 运行生命周期与 Pi 行为测试

> 实现运行事件、模型文本增量、主动取消和内存续跑。逐项测试多工具、协议错误、模型截断及流中断。将会话状态修改集中在循环中，向观察者提供只读事件。沿用 M1 的公共调用方式。

**验收**

- 一批两个调用，一成一败，两个结果都按声明顺序、原 ID 写回。助手消息同时含文字和工具调用时仍执行工具。
- 流未完成、ID 重复、输出截断各有独立用例。即使最后一段参数看起来像合法 JSON，截断调用的执行次数仍为零。
- 模型流和工具运行过程中均可取消。取消后运行权释放，已完成的工具调用保留结果。调用方直接取消 Python Task 时，收尾后继续传播 `CancelledError`。
- 工具结果提交后模型请求失败，显式续跑从工具结果之后请求模型，已经完成的 handler 调用次数保持为一。
- 为运行、轮次、消息和工具事件提供 `run_id`、运行内序号及适用的轮次或调用 ID。每个已启动的 run 发出一次结束事件，同一会话并发启动第二个 run 会得到明确错误。

### M3 · 真实模型适配（独立集成阶段）

> 为通用模型协议实现一个真实适配器。首选支持函数调用的 Chat Completions 协议，模型、端点和认证由调用方配置。适配器负责声明转换、流式分片组装、停止原因和工具结果序列化。使用协议样本做离线回归，并在选定模型上完成直接回答和工具往返各一次。

**验收**

- 用协议样本覆盖两个调用的参数交错到达、文本和调用混合、截断与断流。以调用索引组装分片，保留供应商返回的调用 ID。[函数调用与流式示例](https://developers.openai.com/api/docs/guides/function-calling)
- 检查第二次实际发出的请求载有完整助手调用和配对的工具消息，模型回复包含测试函数运行时产生的值。记录所用模型和请求次数。
- 从干净环境安装构建的 wheel，运行公共 API 冒烟测试和全部离线测试。基础安装可独立运行 M1、M2，模型 SDK 通过适配器的可选依赖安装。

**核心完成条件**为 M1、M2 的公共接口测试通过，且构建的 wheel 能在干净环境中安装并运行这些测试。**模型适配完成条件**为 M3 的协议样本和真实端点验收通过，可在选定模型服务后单独交付。

## 6. 后续扩展

| 需求 | 接入位置与实现依据 |
| --- | --- |
| 更完整的 Pi 交互 | 在轮次边界加入 steering 和 follow-up。并行执行时保留工具声明顺序写回结果。每项扩展增加对应的 Pi 行为测试。 |
| 权限与审批 | 在参数校验与 handler 调用之间等待授权决定。调用方注入主体和策略，拒绝时写回同 ID 结果并记录原因。 |
| 可审计与恢复 | 以 run、turn、call 关联运行记录。需要可靠审计时，在外部副作用之前持久化执行意图，完成后写入脱敏结果和检查点。 |
| 失败重试 | 模型请求和单个工具分别配置重试。对有副作用的写入，使用业务幂等键核对结果。`tool_call_id` 用于会话消息配对。 |
| 评测 | 用脚本模型稳定复现协议行为，用真实模型和固定的工具数据评估选择工具、参数正确性、最终回答、时延与成本。 |
